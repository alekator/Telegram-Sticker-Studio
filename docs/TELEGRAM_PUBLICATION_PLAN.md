# Публикация в Telegram: техническое решение

Статус: исследование на 2026-11-23. Авторизация, экспорт, проверка и публикация ещё не реализованы. Работа офлайн применима к локальному импорту и подготовке после установки компонентов; авторизация и публикация требуют сеть Telegram.

## Существующая база

M1.1 (`47844a8f7304fdcd26160bf5faf88bc71594b66c`) сохраняет JSON схемы 1 со ссылками на исходные файлы, поддерживает асинхронный импорт, галерею и предпросмотр. `StickerForge.Telegram` пока содержит пустой шаблон; валидатора, MTProto и экспорта нет. FFmpeg/FFprobe для видео ищутся локально или в PATH, их автоматическая поставка не реализована. Проекты M1.2+ схемы 2 не открываются: храните их оригиналы и `.assets` с архивной версией, миграции нет.

## Выбор клиента

Основной кандидат — [WTelegramClient](https://github.com/wiz0u/WTelegramClient), MIT, C#/.NET; [NuGet 4.4.11](https://www.nuget.org/packages/WTelegramClient/4.4.11) выпущен 19 ноября 2026 года и заявляет API layer 231. Это кандидат для проверки, зависимость не добавлена; перед принятием закрепить версию, проверить транзитивные лицензии, доступность актуального layer и сценарии на трёх ОС. Вызовы Telegram остаются за портом Application и адаптером Telegram, без собственного MTProto.

Альтернатива — [официальный TDLib](https://github.com/tdlib/td): [API создания набора](https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1create_new_sticker_set.html) существует, но его C++ runtime и выбор поддерживаемой .NET-обёртки требуют отдельной проверки сборок, лицензий и поставки. Bot API не заменяет заданный вход от пользователя и имеет другую модель владения. Не выбирать непроверенный wrapper только по названию.

## Авторизация и хранение

- Собственный `api_id`/`api_hash` регистрируются по [правилам Telegram](https://core.telegram.org/api/obtaining_api_id); модель распространения и защиты учётных данных приложения нужно согласовать до реализации. Не извлекать их из других клиентов. Код входа, возможный пароль 2FA и дополнительные этапы вводятся пользователем; их нельзя писать в логи или проект. Асинхронный UI не должен блокироваться во время ожидания кода. [Описание авторизации](https://core.telegram.org/api/auth).
- WTelegramClient сохраняет ключи сессии в зашифрованном файле; согласно [FAQ](https://github.com/wiz0u/WTelegramClient/blob/master/FAQ.md), по умолчанию ключом может быть `api_hash`, который нельзя считать надёжным секретом в распространяемом приложении. Предусмотреть случайный независимый `session_key`, защищённый хранилищем ОС (Windows DPAPI/Credential Manager, macOS Keychain, Linux Secret Service); файл сессии в приватном каталоге пользователя с ограниченными правами. При недоступном хранилище не делать тихий небезопасный fallback: предложить повторный вход или явно согласованный защищённый режим. Адаптеры и их поведение должны пройти проверку на каждой ОС.
- Отдельная сессия на аккаунт, пользовательский выход и отзыв сессии. Сессии, токены, коды и идентификаторы авторизации не должны попадать в `.stickerforge`, резервные копии проекта, логи, Git или отчёты об ошибках.

## Публикация и восстановление после сбоев

1. Локально подготовить и проверить все файлы и эмодзи; запросить имя и короткое имя, проверить доступность через `stickers.checkShortName` или предложить через `stickers.suggestShortName`. Создание — только по явной кнопке пользователя.
2. Авторизоваться, загрузить файлы по Telegram API, получить документы через `messages.uploadMedia`; сопоставить каждый с `inputStickerSetItem`, в том числе строкой emoji. Создать набор через `stickers.createStickerSet` с вектором начальных элементов; при необходимости добавлять остальные через `stickers.addStickerToSet`. Метод допускает пользователей; детали и ошибки описаны в [API стикеров](https://core.telegram.org/api/stickers) и [createStickerSet](https://core.telegram.org/method/stickers.createstickerset). Лимиты и сочетания типов проверить реальными интеграционными тестами, а не предполагать идентичность Bot API.
3. После подтверждения сервера сохранить ID/access hash набора и document ID каждого элемента, короткое имя, порядок, хеш подготовленного файла и состояние операции в локальном журнале без секретов. Ссылка `https://t.me/addstickers/<short_name>` показывается после подтверждения набора сервером.
4. Восстановление не обещает exactly-once: при потере ответа перед повтором запросить набор по short name, проверить владельца и сравнить ID/содержимое с журналом. Если нельзя однозначно доказать соответствие загруженного элемента и записи, остановиться и попросить пользователя разрешить расхождение; повторная отправка вслепую может создать дубликат. Не считать занятое имя доказательством владения. Частичное состояние явно показать и позволить продолжить или отменить; отмена не удаляет уже созданный набор.
5. Ограничить параллелизм загрузок, поддержать отмену и прогресс, экспоненциальную задержку для временных ошибок. Для `FLOOD_WAIT_X` ждать указанное сервером время, не обходить лимит; ошибки авторизации, прав и формата не повторять автоматически. См. [ошибки API](https://core.telegram.org/api/errors). Предварительно проверить поведение WTelegramClient, включая встроенные повторы, чтобы не удваивать их.

## Подготовка и проверка медиа

Экспортировать в отдельную временную директорию, не изменяя оригиналы; атомарно выдавать готовые файлы после проверки. PNG/WebP — SkiaSharp, WebM/VP9 — FFmpeg при подтверждённой поддержке `libvpx-vp9`, FFprobe и декодер для независимой проверки результата. Сохранение альфы VP9 требует проверки реальным декодированием прозрачных кадров, а не только metadata/pixel format; недоступность прозрачного кодирования — явная ошибка. Перед поставкой подтвердить источник FFmpeg, SHA-256, лицензии и условия сборки; на текущем этапе поставка не решена.

Для профиля импорта Telegram: статический PNG/WebP до 512 KB, одна сторона 512 px, другая не более 512 px, прозрачный слой; WEBM/VP9 до 256 KB, до 3 с, до 30 fps, без аудио, аналогичные размеры. [Руководство импорта](https://core.telegram.org/import-stickers) требует alpha для видео, в то время как [руководство VP9](https://core.telegram.org/stickers/webm-vp9-encoding) отдельно перечисляет основные параметры; валидировать консервативно и подтвердить на сервере. Цикл рекомендуется. Минимум одно emoji на стикер; правила длины, смешанные форматы, размер пачки и правила имён проверять для конкретного MTProto layer. TGS из GIF/видео не генерировать.

## Этапы после утверждения

1. Утвердить модель учётных данных, OS-хранилищ и UX для схемы 2; добавить контракт публикации и тесты без сети.
2. Сделать локальную подготовку и валидатор с тестами форматов, альфы и сохранности оригиналов; решить поставку FFmpeg.
3. Добавить изолированный MTProto-адаптер и авторизацию с безопасным хранилищем, тесты на Telegram test DC.
4. Реализовать журнал, публикацию, примирение неопределённых результатов и отказоустойчивость; проверить аккаунтом с явным разрешением.
5. Соединить с утверждённым UX; проверить Windows/macOS/Linux и большие наборы. До этого публичная готовность не заявляется.
