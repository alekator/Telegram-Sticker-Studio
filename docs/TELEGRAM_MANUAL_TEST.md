# Telegram publishing: current status and acceptance plan

The gallery opens an experimental Avalonia publication window. It accepts a title, short name, emoji per item, API credentials and stepwise WTelegramClient login. Static PNG/WebP are prepared as WebP with a 512-pixel long edge; the source is untouched. [Telegram MTProto documentation](https://core.telegram.org/api/stickers) specifies `image/webp` for static documents; the [import guide](https://core.telegram.org/import-stickers) describes size and transparency. Actual server acceptance, document attributes and server-side document IDs have not been verified.

The local vault encrypts the API credentials and a random session key with AES-256-GCM and PBKDF2-HMAC-SHA256 (600,000 iterations, random salt). WTelegramClient encrypts its session using that independent key. The vault password is not stored and library logging is disabled. The password-based approach is used on all three platforms; native OS credential stores and independent security review remain outstanding. Lost passwords cannot recover the session. Credential inputs are not persisted in the project. No real credentials were used in development.

Before `stickers.createStickerSet`, a durable local record reserves the short name and uploaded document IDs. A second attempt is blocked. Recovery checks the owned set and exact IDs; ambiguity does not trigger another create. Records contain no auth keys, but cannot resume a partially created set by adding missing items. Interrupted or malformed records require manual investigation. There is no automatic cleanup or account-specific journal partition; concurrent attempts to create a reservation are blocked by atomic file creation. Cancellation is cooperative between WTelegramClient RPCs, not during them. Rate-limit errors are surfaced, not automatically scheduled; a rate limit after the create request is treated as uncertain.

There is no append-to-set flow. A single create call submits all items; `stickers.addStickerToSet` recovery is not implemented. Emoji validation checks non-empty text, not Unicode emoji validity. GIF/video publication and VP9 export remain future work. Existing gallery/import and project format are unchanged.

## Manual acceptance plan — only after security review

Use a dedicated Telegram test account and harmless test images. Obtain a separate API ID/hash through [Telegram](https://core.telegram.org/api/obtaining_api_id). After review, check first login (phone, code, optional 2FA), restart and resume, wrong vault password, logout, import of at least two transparent PNG/WebP files, emoji assignment, unavailable short name, creation, link opening, order and alpha in Telegram. Disconnect during upload and around creation, restart and verify that recovery never duplicates a pack. Check FloodWait messaging, cancellation and original file hashes. Repeat platform-specific storage and UI checks on Windows, macOS and Linux. This plan has not been executed.
