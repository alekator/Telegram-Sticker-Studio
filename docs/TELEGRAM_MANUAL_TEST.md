# Telegram publishing: current status and acceptance plan

## Readiness: NOT READY

Do not enter API credentials or attempt a Telegram login. The prototype's sign-in and publication controls remain disabled. Encrypted account-bound journal and partial-set recovery now exist and have fake-API tests, but server-side behavior of upload, generated attributes, ownership, document identifiers and file-reference expiry is unverified. Neither the complete sign-in/logout lifecycle nor its security has been tested against a real server. Emoji validation and safe cleanup of completed journals remain incomplete. These are blockers for enabling the workflow.

Security audit so far: the vault serializes credentials in memory, encrypts its output with AES-GCM and writes ciphertext to a temporary file before its first atomic move. The session key is random and stored inside the encrypted vault; WTelegramClient is configured with that key and its logging callback is disabled. Passwords, codes and keys remain managed strings in process memory and cannot be reliably wiped. Platform-specific file permissions, backups, crash dumps, other applications' access and WTelegramClient's precise installed-version session behavior have not been comprehensively assessed. The new journal encrypts document references and emoji and binds them to the account ID and short name; the path itself exposes those identifiers. Never include vault, session, journal, logs, memory dumps, phone numbers, API hash, 2FA password or verification codes in reports or screenshots.

## Future manual test — execute only after blockers are resolved

1. Obtain an API ID and API hash from [Telegram's API development tools](https://core.telegram.org/api/obtaining_api_id). Use a dedicated test account; keep the hash private and use a unique strong local vault password. Do not commit credentials or session files.
2. Once controls are enabled after review, open the vault, enter the account's phone number, supply the requested code and, if requested, the 2FA password. Verify reconnect after closing and reopening; use Log out to revoke the session and check Telegram's active sessions. Do not use the prototype while controls are disabled.
3. Import two or three harmless transparent PNG/WebP images, name the pack, choose an available short name, assign emoji, validate and publish. Save the resulting link and open it in Telegram; check the stickers, order, emoji and transparency.
4. If needed, delete the test set using Telegram's [@Stickers management interface](https://t.me/stickers) or an official Telegram client. Confirm that the intended set belongs to the test account before deletion.
5. Test a connection loss before creation, during creation and during any later addition. Restart the app, reconnect and use recovery. Verify the existing set and each item in Telegram before any further attempt; do not manually repeat creation if its outcome is unclear. Confirm that no duplicate set or sticker was added.
6. Check logout, wrong vault password, FloodWait, cancellation and source-file hashes. Capture only sanitized error text and application version; exclude secrets and the files listed above. Repeat platform checks separately on Windows, macOS and Linux.

The gallery opens an experimental Avalonia publication window, but login and publication controls are disabled. Static PNG/WebP are prepared as WebP with a 512-pixel long edge; the source is untouched. [Telegram MTProto documentation](https://core.telegram.org/api/stickers) specifies `image/webp` for static documents; the [import guide](https://core.telegram.org/import-stickers) describes size and transparency. Actual server acceptance, document attributes and server-side document IDs have not been verified.

The local vault encrypts the API credentials and a random session key with AES-256-GCM and PBKDF2-HMAC-SHA256 (600,000 iterations, random salt). WTelegramClient encrypts its session using that independent key. The vault password is not stored and library logging is disabled. The password-based approach is used on all three platforms; native OS credential stores and independent security review remain outstanding. Lost passwords cannot recover the session. Credential inputs are not persisted in the project. No real credentials were used in development.

Before `stickers.createStickerSet`, an encrypted local record reserves the account, short name, uploaded document references and emoji. A second create is blocked. Recovery reads the owned set and checks that its nonempty document IDs are a subset of the expected IDs before adding missing items, querying again before every add. If an add response is lost, a later recovery checks the server first. Expired references, legacy journals, mismatched IDs or unreadable journals require manual investigation; no unsafe re-upload is attempted. Concurrent same-pack operations use a file lock. Cancellation is cooperative between WTelegramClient RPCs, not during them. FloodWait is surfaced, not automatically scheduled; a failure after a create or add request is treated as uncertain.

Partial-set recovery and logout are covered by fake-API tests only; they are not validated against Telegram. Logout deletes the local vault and session after successful server revocation. To avoid destroying the key for a saved journal, logout is blocked while any account journal exists; a safe completed-journal cleanup flow is still needed. Emoji validation checks non-empty text, not Unicode emoji validity. GIF/video publication and VP9 export remain future work. Existing gallery/import and project format are unchanged.

## Manual acceptance plan — only after security review

Use a dedicated Telegram test account and harmless test images. Obtain a separate API ID/hash through [Telegram](https://core.telegram.org/api/obtaining_api_id). After review, check first login (phone, code, optional 2FA), restart and resume, wrong vault password, logout, import of at least two transparent PNG/WebP files, emoji assignment, unavailable short name, creation, link opening, order and alpha in Telegram. Disconnect during upload and around creation, restart and verify that recovery never duplicates a pack. Check FloodWait messaging, cancellation and original file hashes. Repeat platform-specific storage and UI checks on Windows, macOS and Linux. This plan has not been executed.
