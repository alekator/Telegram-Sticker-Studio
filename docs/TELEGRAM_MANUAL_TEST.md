# Telegram publishing: current status and acceptance plan

## Readiness: NOT READY

Do not enter API credentials or attempt a Telegram login. The prototype's sign-in and publication controls are disabled. The journal stores only document IDs: after a restart it cannot reconstruct `InputDocument` references and emoji for the missing items, and partial-set append with `stickers.addStickerToSet` is not implemented. Server-side behavior of upload, generated attributes, ownership and document identifiers has not been verified. Neither the full sign-in/logout lifecycle nor its security has been reviewed against a real server. A completed journal alone does not prove that a partially created set can be resumed safely.

Security audit so far: the vault serializes credentials in memory, encrypts its output with AES-GCM and writes ciphertext to a temporary file before its first atomic move. The session key is random and stored inside the encrypted vault; WTelegramClient is configured with that key and its logging callback is disabled. Passwords, codes and keys remain managed strings in process memory and cannot be reliably wiped. Platform-specific file permissions, backups, crash dumps, other applications' access, WTelegramClient's precise installed-version session behavior and logout/revocation failure handling have not been comprehensively assessed. The journal contains document IDs and short names, not account-bound authorization keys, and is not encrypted or account-partitioned. Never include vault, session, journal, logs, memory dumps, phone numbers, API hash, 2FA password or verification codes in reports or screenshots.

## Future manual test — execute only after blockers are resolved

1. Obtain an API ID and API hash from [Telegram's API development tools](https://core.telegram.org/api/obtaining_api_id). Use a dedicated test account; keep the hash private and use a unique strong local vault password. Do not commit credentials or session files.
2. Once controls are enabled after review, open the vault, enter the account's phone number, supply the requested code and, if requested, the 2FA password. Verify reconnect after closing and reopening; use Log out to revoke the session and check Telegram's active sessions. Do not use the prototype while controls are disabled.
3. Import two or three harmless transparent PNG/WebP images, name the pack, choose an available short name, assign emoji, validate and publish. Save the resulting link and open it in Telegram; check the stickers, order, emoji and transparency.
4. If needed, delete the test set using Telegram's [@Stickers management interface](https://t.me/stickers) or an official Telegram client. Confirm that the intended set belongs to the test account before deletion.
5. Test a connection loss before creation, during creation and during any later addition. Restart the app, reconnect and use recovery. Verify the existing set and each item in Telegram before any further attempt; do not manually repeat creation if its outcome is unclear. Confirm that no duplicate set or sticker was added.
6. Check logout, wrong vault password, FloodWait, cancellation and source-file hashes. Capture only sanitized error text and application version; exclude secrets and the files listed above. Repeat platform checks separately on Windows, macOS and Linux.

The gallery opens an experimental Avalonia publication window. It accepts a title, short name, emoji per item, API credentials and stepwise WTelegramClient login. Static PNG/WebP are prepared as WebP with a 512-pixel long edge; the source is untouched. [Telegram MTProto documentation](https://core.telegram.org/api/stickers) specifies `image/webp` for static documents; the [import guide](https://core.telegram.org/import-stickers) describes size and transparency. Actual server acceptance, document attributes and server-side document IDs have not been verified.

The local vault encrypts the API credentials and a random session key with AES-256-GCM and PBKDF2-HMAC-SHA256 (600,000 iterations, random salt). WTelegramClient encrypts its session using that independent key. The vault password is not stored and library logging is disabled. The password-based approach is used on all three platforms; native OS credential stores and independent security review remain outstanding. Lost passwords cannot recover the session. Credential inputs are not persisted in the project. No real credentials were used in development.

Before `stickers.createStickerSet`, a durable local record reserves the short name and uploaded document IDs. A second attempt is blocked. Recovery checks the owned set and exact IDs; ambiguity does not trigger another create. Records contain no auth keys, but cannot resume a partially created set by adding missing items. Interrupted or malformed records require manual investigation. There is no automatic cleanup or account-specific journal partition; concurrent attempts to create a reservation are blocked by atomic file creation. Cancellation is cooperative between WTelegramClient RPCs, not during them. Rate-limit errors are surfaced, not automatically scheduled; a rate limit after the create request is treated as uncertain.

There is no append-to-set flow. A single create call submits all items; `stickers.addStickerToSet` recovery is not implemented. Emoji validation checks non-empty text, not Unicode emoji validity. GIF/video publication and VP9 export remain future work. Existing gallery/import and project format are unchanged.

## Manual acceptance plan — only after security review

Use a dedicated Telegram test account and harmless test images. Obtain a separate API ID/hash through [Telegram](https://core.telegram.org/api/obtaining_api_id). After review, check first login (phone, code, optional 2FA), restart and resume, wrong vault password, logout, import of at least two transparent PNG/WebP files, emoji assignment, unavailable short name, creation, link opening, order and alpha in Telegram. Disconnect during upload and around creation, restart and verify that recovery never duplicates a pack. Check FloodWait messaging, cancellation and original file hashes. Repeat platform-specific storage and UI checks on Windows, macOS and Linux. This plan has not been executed.
